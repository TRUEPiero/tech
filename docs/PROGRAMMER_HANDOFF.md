## 2. Рекомендуемый способ переноса

Для существующего сайта, в том числе на «1С-Битрикс: Управление сайтом», рекомендуется перенести нужные блоки и калькулятор в текущую архитектуру.

1. Сохранить маршруты, формы, меню, SEO и дизайн действующего сайта.
2. Собрать клиентский калькулятор как отдельный React-компонент или перенести его состояние и интерфейс в принятую на сайте технологию. Поведение должно остаться тем же.
3. Использовать независимые функции lib/project-configuration.ts для структуры помещений, суммирования выбранных потребностей, проверки контакта и формирования JSON.
4. Перенести типовые комнаты и их редактор. Два серверных действия - чтение и сохранение шаблонов - подключить к базе и авторизации действующего сайта.
5. Подключить утвержденный расчет оборудования отдельной чистой функцией. Один и тот же результат должен использоваться в нижнем итоге и JSON.
6. Согласовать интеграцию Project Tool отдельным этапом. Сейчас внешней отправки нет.

Преимущество: сохраняются текущий сайт и его инфраструктура. Работа, которую нужно сделать: адаптировать стили, обработчики, хранение и авторизацию.

Альтернатива - развернуть прототип отдельным приложением. Он использует React 19, TypeScript, Vinext/Vite и Cloudflare Workers с D1. Преимущество - меньше переделок интерфейса. Ограничение - это отдельное приложение с собственной инфраструктурой. Его нельзя просто скопировать в каталог PHP-сайта и ожидать работы серверных функций.

## 4. Поведение, которое требуется сохранить

- Этажи: цокольный, первый, второй, третий. Один тип этажа добавляется один раз.
- На каждом этаже можно добавлять несколько комнат одинакового типа. Комната имеет собственный ID.
- При добавлении комнаты берется копия ее шаблона. Изменения одной комнаты не меняют соседние комнаты или исходный шаблон.
- Общее: площадь в м² и наличие одной вентустановки для объекта.
- Свет: общий счетчик релейных групп света, умных розеток и вентиляторов; отдельно диммирование, DALI и LED. Вентилятор с релейным включением и выключением учитывается в этом общем счетчике.
- Отопление: зоны радиаторов, контуры водяного пола, зоны электрического пола, фанкойлы.
- Датчики: количество CO₂, движения и мокрых зон. Мокрая зона не является заранее определенным числом датчиков или кранов.
- Шторы: общее количество приводов без выбора разновидности.
- Кондиционеры: наличие в каждой комнате.
- Управление: по одной панели каждого выбранного типа P4/P6/P8 и один сценарный выключатель на 4, 6 или 8 клавиш либо «Нет» в каждой комнате. Панели отмечаются независимо. Если панель заменяет выключатель, у выключателя выбирается «Нет».
- Начальное управление: P4 без выключателя в прихожей и коридоре. В остальных комнатах при сумме relay + dimming + dali + led > 3 или curtains > 2 ставится четырехклавишный выключатель. Условие «или» и базовый выбор четырех клавиш - рабочие допущения. У LED для этого условия считается число групп, без умножения на два канала.
- При добавлении комнаты копируется ее управление из шаблона. Последующие правки света и штор не перезаписывают управление. Все поля управления доступны в редакторе «Типовые комнаты».
- На вкладке «Управление» под названием комнаты показаны текущие количества света, отопления, штор и кондиционеров. Свет - сумма релейных групп, диммирования, DALI и LED без пересчета в аппаратные каналы. Отопление - сумма выбранных зон радиаторов, контуров водяного пола, зон электрического пола и фанкойлов. Кондиционер отображается как 1 или «нет». Сводка обновляется из текущей конфигурации при изменениях других вкладок.
- Общий релейный счетчик объединяет свет, розетки и вентиляторы. Поэтому сводка «Свет» и начальное условие выбора управления также включают розетки и вентиляторы. Отдельно восстановить число только осветительных групп из этих данных нельзя.
- Изменения сразу отражаются в потребностях и формируемом JSON. Будущая цена должна пересчитываться тем же способом, без отдельной кнопки «Пересчитать».
- Никакие отрицательные количества не допускаются. Удаленные комнаты и этажи не участвуют в итогах.
- Данные конкретной клиентской конфигурации сейчас находятся только в памяти открытой страницы. Обновление страницы начинает новую конфигурацию. Скачанный JSON является отдельным снимком.

## 5. Типовые комнаты и база

На дату подготовки пакета в опубликованной таблице calculator_settings не было сохраненных пользовательских строк. Поэтому действуют исходные 30 шаблонов из lib/calculator-room-presets.ts. Их снимок приложен как docs/examples/room-defaults.json.

После сохранения через редактор шаблоны живут в базе и имеют приоритет над исходным файлом. При более позднем переносе нужно забрать актуальные значения повторно; одного архива исходников уже может быть недостаточно для этих данных.

Хранится одна запись с JSON-набором, ревизией и служебными полями. Сохранение проверяет ожидаемую ревизию: если другая вкладка уже изменила таблицу, сервер возвращает конфликт, а не затирает значения.

Старые записи без controls читаются через storedSettingsContentSchema: недостающие поля управления вычисляются из сохраненных количеств комнаты. Существующие поля, ревизия и запись в базе при чтении не изменяются. Явно сохраненный выбор управления не заменяется рекомендацией. Новая запись требует controls во всех комнатах; устаревшая вкладка редактора не может молча удалить новые поля. SQL-схема не менялась.

На другом хостинге можно использовать действующую базу сайта. Таблицу и проверку ревизии нужно перенести. Рабочая D1-база не входит в ZIP. Миграция создает только структуру, стартовые значения читает код.

## 6. Авторизация и формы

В Sites владелец определяется сервером по заголовкам, выставляемым платформой, и CALCULATOR_ADMIN_EMAIL. За пределами Sites нельзя доверять таким заголовкам, присланным браузером. Нужно заменить проверку на действующую серверную сессию и роль администратора сайта. Секреты и данные авторизации в архив не включены.

Форма расчета щита требует площадь, хотя бы одну комнату, один контакт и согласие. Контакт выбирается из email, Telegram или WhatsApp. Она готовит JSON в браузере через Blob и не выполняет POST, отправку письма или сообщения.

Главная форма сайта также остается в демонстрационном режиме. Она вызывает локальный POST /api/leads. В обработчике есть заготовка отправки JSON на два адреса BITRIX_WEBHOOK_URL и LEAD_EMAIL_WEBHOOK_URL. Пока хотя бы один адрес отсутствует, внешние запросы не выполняются и возвращается demo: true. Если задать оба адреса, обработчик начнет выполнять POST на оба. Это общий формат webhook, а не готовое создание лида методом Bitrix REST. Для подключения нужны адаптер формата, обработка частичной доставки и защита от дублирования при повторах.

Bitrix, email-уведомления, Telegram, WhatsApp и Project Tool сейчас не подключены. Настоящие видео еще не загружены. В главной форме обязательны имя, телефон и согласие, email необязателен. В отдельном запросе щита используется только один выбранный контакт. Тексты оператора и политики обработки данных еще не предоставлены.

## 7. Расчет оборудования: пока не реализован

estimate.totalRub имеет значение null, а не 0. equipmentSeries также пока не назначается. Отсутствие расчета не означает бесплатное оборудование.

Правило Сергея: при площади больше 250 м² использовать Pro, при площади меньше 250 м² - Lite. Для ровно 250 м², головного комплекта и других спорных пунктов подготовлены предложения в CALCULATION_PROPOSAL.md. Расчет нельзя подменять общей ценой за м² с главной страницы.

Для LED согласован средний расход двух каналов на одну выбранную группу. Для шестиканальных DM-060LED / LDM-060LED количество модулей = округление вверх (сумма LED-групп объекта × 2 / 6). Ноль групп дает ноль модулей. Клиенту не нужно выбирать тип ленты. В JSON ledGroups остается числом выбранных групп; умножение на два относится к будущему подбору оборудования, а не к сохранению пользовательского ввода.

После согласования необходимо создать версионируемый прайс РРЦ, таблицу соответствий потребностей оборудованию и функцию подбора с округлением числа модулей вверх. Необходимо различать пустую цену и ноль, устройства и каналы, DALI-группы и адреса, мокрые зоны и физические датчики.

Перед публикацией расчета проверить: 250 м² и соседние значения; переход 6/7 релейных каналов; переход 3/4 LED-групп; нулевые количества; отсутствие мокрых зон; 3/4 шторы; отсутствующую цену; несколько одинаковых комнат; удаление последнего этажа. Перечень неполных правил должен сохраняться вместе с результатом.

## 8. Запуск исходного прототипа

Нужны Node.js 22.13 или новее, npm и Linux/WSL. Текущие вспомогательные скрипты используют Bash и GNU timeout; команды ниже рассчитаны на Linux/WSL. Python 3 нужен только для обновления документов и упаковки. В чистой среде разработчика зависимости устанавливаются из package-lock.json. Все команды выполнять в корне распакованного проекта:

```bash
npm ci
npx wrangler d1 execute DB --local --config wrangler.local.jsonc --persist-to .wrangler/state --file drizzle/0000_watery_agent_brand.sql
npm run dev
```

Миграция выше применяется один раз к новой локальной базе. Она содержит CREATE TABLE без IF NOT EXISTS; повторный запуск на уже созданной таблице даст ошибку. Не заменять --local на --remote. Открыть локальный адрес, который напечатает Vite; калькулятор находится по /calculator.

В другой консоли, после остановки dev при необходимости, собрать приложение и запустить существующие тесты:

```bash
npm run build
node --test tests/calculator-defaults.test.mjs tests/calculator-api.test.mjs tests/project-configuration.test.mjs tests/rendered-html.test.mjs
```

Локальные параметры DB, site-creator-d1 и технический ID совпадают в wrangler.local.jsonc и vite.config.ts; состояние находится в .wrangler/state. Пустая таблица дает стартовые шаблоны. Отсутствующая таблица или недоступная база выводит сообщение о невозможности загрузить шаблоны.

Публичное чтение калькулятора не требует настройки владельца. Локальный редактор по умолчанию не получает удостоверенную личность Sites. Одного заполнения CALCULATOR_ADMIN_EMAIL недостаточно для получения прав: требуется серверная идентификация. Логику сохранения можно проверить имеющимися изолированными тестами; в целевом сайте редактор подключается к его авторизации. Не переносить тестовую подстановку заголовков в публичный продакшен.

В архиве .env.example содержит только имя переменной для администрирования. Реальные значения задаются отдельно в целевой среде. Служебная .openai/hosting.json относится к исходному приватному Site и не является готовой конфигурацией чужого продакшена. Для отдельного размещения нужен собственный проект и его привязки, либо адаптация под сервер существующего сайта.

## 9. Проверка перед приемкой переноса

1. Сравнить внешний вид главной страницы и калькулятора с прототипом.
2. Проверить автоматическое заполнение, независимость одинаковых комнат и удаление объектов.
3. Проверить сохранение шаблонов после перезагрузки и запрет записи для обычного посетителя.
4. Проверить все три способа указания контакта и соответствие скачанного JSON текущим настройкам.
5. Подтвердить отсутствие отправки до отдельного подключения интеграций.
6. После реализации цен сверить спецификацию и сумму с утвержденными контрольными примерами.
7. Проверить viewport: 320×568, 375×667, 390×844, 412×915, 768×1024, 1024×768, 1280×800, 1440×900, 1920×1080, 2560×1440. Не должно быть горизонтальной прокрутки страницы, наложений и обрезанного текста. Основной контейнер - до 1440 CSS px, интерактивные зоны - от 44×44 px.
8. Проверить Safari/iPhone, Chrome/Android, Chrome/macOS/Windows, Safari/macOS, Edge и Firefox. Проверки в среде прототипа не заменяют приемку в целевом продакшене.

Публикация на боевом сайте, подключение отправки и изменение прав доступа входят в отдельный этап работы программиста после согласования с Сергеем.

## 10. Контракт редактора шаблонов

GET /api/calculator-defaults возвращает объект { ventilation, rooms, revision, updatedAt }. Начальная ревизия 0, updatedAt = null. После сохранения ревизия возрастает. Ответы имеют Cache-Control: no-store. При ошибке чтения возвращается 503.

PUT /api/calculator-defaults принимает { ventilation, rooms, revision }. Передавать полный набор всех 30 комнат; поля комнаты перечислены в examples/room-defaults.json и roomPresetSchema. Поле updatedAt из ответа GET не входит в тело PUT. Автор берется из серверной сессии, поле updated_by клиент не присылает.

| Ответ PUT | Причина |
| --- | --- |
| 200 | Сохранено; возвращены значения с новой revision и updatedAt. |
| 400 | Неверный JSON или данные, неполный набор комнат, неверные количества или controls. |
| 403 | Нет прав либо Origin не соответствует origin текущего запроса. |
| 409 | Переданная ревизия устарела. Нужно перечитать данные и согласовать правки. |
| 413 | Превышен лимит тела запроса 65 536 байт по Content-Length или 65 536 символов после чтения. |
| 415 | Content-Type не начинается с application/json. |
| 503 | Сбой базы при сохранении. |

Структура SQL: id (первичный ключ), payload (JSON), revision, updated_at, updated_by. Используется запись с id = rooms. При переносе в другую СУБД адаптировать INSERT/UPDATE с проверкой ревизии в одной атомарной операции.

Генератор примеров использует исходный набор, а не живую базу. Если администратор сохранял новые шаблоны, перед следующей передачей выгрузить их отдельно. Сборщик ZIP требует чистого состояния отслеживаемых файлов, не включает .env, .git, node_modules, локальные базы и артефакты сборки.
